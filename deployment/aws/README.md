# Deploying Fresh Grocery on AWS (ECS Fargate + ECR) with Terraform

This guide takes you from an empty AWS account to the running shop, one step at a time, and back to nothing
when you are done. You type every command yourself; nothing runs automatically.

> **It costs money while it runs.** With the dev settings in `terraform.tfvars` it is roughly **US$ 1 per hour
> (about US$ 700 per month)**. Run `terraform destroy` (step 11) as soon as you are done testing, and set up an
> AWS Budgets alert (step 0). The [cost section](#what-it-costs) explains where the money goes.

## What gets created

```text
                      internet
                         |
            +------------v------------+      public subnets (2 zones)
            |  Application Load       |      /api/*, /media/*, /delivery-media/*  -> api-gateway
            |  Balancer (HTTP/HTTPS)  |      everything else                       -> frontend (React shop)
            +------------+------------+
                         |
   private subnets (2 zones): no access from the internet; out through a NAT gateway
   +---------------------v----------------------------------------------------------+
   |  ECS Fargate (cluster grocery-dev)                                             |
   |    frontend, api-gateway, auth, customer, store, product, product-read,        |
   |    inventory, cart, order, payment, delivery, notification, report, platform   |
   |    schema-registry, kafka-connect (Debezium), elasticsearch                    |
   |    The services find each other by DNS: auth-service.grocery.internal:8080     |
   |                                                                                |
   |  RDS MySQL 8.4   Amazon MSK (Kafka)   ElastiCache Redis   EFS (photos,         |
   |  13 databases    one broker per zone  TLS + users         invoices, index)     |
   +--------------------------------------------------------------------------------+
   ECR: one image repository per service   Secrets Manager: every password, generated
   CloudWatch Logs: every container's logs Container Insights: CPU and memory per service
```

| Part of the app | On AWS | Why |
|---|---|---|
| 14 Spring Boot services and the React shop | **ECS Fargate** services | No servers to manage; rolling updates and automatic rollback |
| Docker images | **Amazon ECR** (private, scanned for vulnerabilities, tags cannot be overwritten) | |
| MySQL (13 service databases) | **Amazon RDS for MySQL 8.4** (see [the database](#the-mysql-database-amazon-rds)) | Backups, patches, failover, encryption and monitoring by AWS |
| Kafka | **Amazon MSK** | Managed Kafka |
| Redis | **Amazon ElastiCache** (TLS, the same limited users as on a laptop) | |
| Schema Registry, Kafka Connect + Debezium | ECS Fargate | AWS has no managed version that fits |
| Elasticsearch 9 | ECS Fargate, data on EFS | Amazon OpenSearch is refused by the app's Elasticsearch 9 client; see [going to production](#going-to-production) |
| Product photos, proof photos, invoices | **Amazon EFS** (encrypted, daily backups) | Shared by all copies of a service, survives restarts |
| Passwords and keys | **AWS Secrets Manager** (generated by Terraform; MySQL's admin password by RDS) | Nothing secret in files or in task definitions |

Not deployed: the AI shopping assistant (off by default: it needs an Ollama server, see `enable_ai_assistant`),
and the developer tools of the laptop setup (Kafka UI, Redis Insight, Mailpit, Kibana, Prometheus, Grafana).
CloudWatch Logs and Container Insights replace the monitoring tools.

## 0. Before you start

- An **AWS account** in which you may create the services above. For a first deployment the simplest is a user or
  role with the `AdministratorAccess` policy, in a sandbox account (ask your team).
- A **budget alert**: AWS console > Billing and Cost Management > Budgets > Create budget > "Monthly cost budget",
  e.g. US$ 100, with your email. AWS then emails you before the bill surprises you.
- About **2 hours** for the first deployment, most of it waiting (Kafka alone takes 20-30 minutes to create).

## 2. Configure AWS credentials

Terraform, the AWS CLI and the scripts all find your credentials by themselves. **Never** write access keys
into a `.tf` or `.tfvars` file, and never commit them.

**Option A (recommended): AWS IAM Identity Center (SSO)**, if your company uses it. Short-lived credentials, no
keys on your disk.

```powershell
aws configure sso                       # once: asks for your SSO start URL, account, role, region; names a profile
$env:AWS_PROFILE = "grocery-dev"        # the profile name you chose; set it in every new terminal
aws sso login                           # when your session has expired (usually every 8-12 hours)
```

**Option B: an access key** of an IAM user (only if you have no SSO).

```powershell
aws configure                           # asks for the access key id, the secret key, the region (ap-south-1), json
```

Or only for the current terminal, with environment variables:

```powershell
# PowerShell
$env:AWS_ACCESS_KEY_ID     = "AKIA..."
$env:AWS_SECRET_ACCESS_KEY = "..."
$env:AWS_REGION            = "ap-south-1"
```

```bash
# macOS / Linux
export AWS_ACCESS_KEY_ID="AKIA..."
export AWS_SECRET_ACCESS_KEY="..."
export AWS_REGION="ap-south-1"
```

**Check** that it works, and that it is the account you expect:

```powershell
aws sts get-caller-identity
```

It prints your account number and user or role. If it fails, nothing else will work: fix this first.

## 4. Adjust the settings

Open `deployment/aws/terraform/terraform.tfvars`. The defaults work as they are; the lines you are most likely
to change:

| Setting | Default | Change it when |
|---|---|---|
| `aws_region` | `ap-south-1` (Mumbai) | You want another region (it must offer all the services; the big ones all do) |
| `environment` | `dev` | You create a second copy (`staging`, `prod`): it changes every resource name |
| `allowed_ingress_cidrs` | everyone | You want only your own IP to reach the shop while testing, e.g. `["203.0.113.7/32"]` |
| `load_demo_data` | `true` | You want an empty shop (always `false` in prod: the demo passwords are public) |
| `use_fargate_spot` | `false` | You want the application tasks about 70% cheaper (they may be restarted now and then) |
| `rds_instance_class` | `db.t4g.medium` | The database needs more power (see [the database](#the-mysql-database-amazon-rds)) |
| `alarm_email` | empty (no alarms) | You want an email when the database runs hot or out of space: your address |

**Secrets** (only if you use them) go into environment variables, never into the file. Terraform reads every
`TF_VAR_<name>` variable as the value of `<name>`:

```powershell
$env:TF_VAR_razorpay_key_secret     = "..."   # with payment_gateway = "razorpay"
$env:TF_VAR_razorpay_webhook_secret = "..."
$env:TF_VAR_mail_password           = "..."   # with Amazon SES, see "Emails with Amazon SES"
```

Every other secret (database passwords, the JWT key ...) is **generated** by Terraform; you never see or type it.

**Check the Kafka version** your region offers, and set `msk_kafka_version` if `3.8.x` is not in the list:

```powershell
aws kafka list-kafka-versions --query "KafkaVersions[?Status=='ACTIVE'].Version" --output text
```

## 5. Initialize, test and create the infrastructure

```powershell
cd deployment/aws/terraform
terraform init          # downloads the AWS provider (the versions in .terraform.lock.hcl)
terraform fmt -check    # the files are formatted the standard way (no output = fine)
terraform validate      # the configuration is valid
terraform test          # 6 tests with a fake AWS: no account needed, costs nothing
```

Now the first real step. `deploy_services` is `false` in `terraform.tfvars`, so this creates the network, the
databases, Kafka, Redis, EFS, the load balancer, the ECR repositories and the cluster, but **no services yet**
(their images do not exist yet).

```powershell
terraform plan -out tfplan   # shows what WOULD be created; changes nothing
```

**Read the plan** before you apply it. At the end it says `Plan: N to add, 0 to change, 0 to destroy.` On a
first run everything is "add". Scroll through the `+` lines: you will recognise the resources from the table at
the top. If you ever see `destroy` you did not expect, stop and find out why.

```powershell
terraform apply tfplan       # creates exactly what the plan showed
```

This takes **25-40 minutes** (MSK and RDS are slow to create; the output shows what is still being created).
At the end Terraform prints its outputs: the shop's address (`application_url`, not working yet) and
`next_steps`. Show them again any time with `terraform output`.

## 6. Build and push the images

From the repository root (a new terminal: `cd` back up):

```powershell
.\deployment\aws\scripts\push-images.ps1
```

```bash
./deployment/aws/scripts/push-images.sh      # macOS / Linux
```

It logs Docker in to your ECR, then builds every image (the 14 services, the frontend and Kafka Connect) and
pushes it with the tag `image_tag` from `terraform.tfvars` (`1.0.0`). The **first run takes long**: each service
compiles inside Docker (Maven downloads its libraries). To rebuild only some images:
`.\deployment\aws\scripts\push-images.ps1 -Images auth-service,frontend`.

You can see the images in the AWS console: ECR > Private repositories > `grocery-dev/...`. Each image is scanned
for known vulnerabilities after the push ("Scan status").

## 7. Prepare MySQL and Kafka (one time)

Two setup tasks run once in the cluster, inside the private network (only they can reach MySQL and Kafka):

```powershell
.\deployment\aws\scripts\run-setup-task.ps1 db-init        # the 13 databases and their users, the Debezium user
.\deployment\aws\scripts\run-setup-task.ps1 kafka-topics   # the topics (the same script as on a laptop)
```

Each one starts the task, waits until it has finished (1-5 minutes), prints its log and says whether it worked.
Both are safe to run again. (`terraform output run_setup_task_commands` shows the plain AWS CLI command instead.)

## 8. Start the services

In `terraform.tfvars`, change

```hcl
deploy_services = true
```

then, in `deployment/aws/terraform`:

```powershell
terraform plan -out tfplan    # now adds the services, their task definitions, DNS names, log groups and autoscaling
terraform apply tfplan
```

Terraform returns after 1-2 minutes, but the services need **3-5 more minutes** to start (Spring Boot, then the
database migrations). Watch them:

```powershell
aws ecs describe-services --cluster grocery-dev --services api-gateway auth-service frontend `
  --query "services[].{service:serviceName,running:runningCount,desired:desiredCount,rollout:deployments[0].rolloutState}" `
  --output table
```

`rollout` turns from `IN_PROGRESS` to `COMPLETED` when a service is healthy. Or in the console: ECS > Clusters >
grocery-dev > Services. A service's logs:

```powershell
aws logs tail /ecs/grocery-dev/auth-service --follow     # Ctrl+C to stop
```

## 9. Connect the event pipeline (one time)

When the services run (their tables exist now), register the Debezium connectors. They pass every change from
MySQL to Kafka (the outbox events, and the products to the search):

```powershell
.\deployment\aws\scripts\run-setup-task.ps1 kafka-connectors
```

It shows every connector's status (all should say `RUNNING`). With `load_demo_data = true` it also publishes the
sample stock, so the search shows products in stock.

## 10. Open the shop

```powershell
terraform output application_url
```

Open that address in your browser (plain `http://` without a certificate). The panels are at `/vendor`,
`/delivery` and `/admin`. With `load_demo_data = true` the demo accounts work, all with the password
`Password@123`: `customer1@grocery.com`, `vendor1@grocery.com`, `delivery1@grocery.com`, `admin@grocery.com`,
`superadmin@grocery.com` (all listed in [docs/local-accounts-and-tools.md](../../docs/local-accounts-and-tools.md)).

> Over plain HTTP the login does **not survive a page reload** (the refresh cookie is only sent over HTTPS, as it
> should be). Everything else works. Set up [HTTPS](#https-and-your-own-domain) to fix it.

### Release a new version

1. Raise `image_tag` in `terraform.tfvars` (e.g. `1.0.1`). Tags cannot be reused: a tag always means the same image.
2. Push **every** image with the new tag: `.\deployment\aws\scripts\push-images.ps1`. (All services run the one
   `image_tag`, so each of them needs an image with it, also the ones that did not change.)
3. `terraform plan -out tfplan` then `terraform apply tfplan`: ECS starts the new tasks, waits until they are
   healthy, then stops the old ones (no downtime). A version that does not start is rolled back by itself.

To go back, set `image_tag` to the previous version and apply again.

### Everyday commands

| What | Command |
|---|---|
| A service's logs | `aws logs tail /ecs/grocery-dev/<service> --follow` |
| A MySQL prompt to the database | `.\deployment\aws\scripts\db-shell.ps1` (see [the database](#the-mysql-database-amazon-rds)) |
| A shell inside a running container | `aws ecs execute-command --cluster grocery-dev --task <task id> --container <service> --interactive --command "/bin/sh"` (needs the [Session Manager plugin](https://docs.aws.amazon.com/systems-manager/latest/userguide/session-manager-working-with-install-plugin.html)) |
| Restart a service (same version) | `aws ecs update-service --cluster grocery-dev --service <service> --force-new-deployment` |
| More CPU / memory / copies for one service | `service_overrides = { "order-service" = { cpu = 1024, memory = 2048, desired_count = 2 } }` in terraform.tfvars, then plan and apply |
| See a generated secret (e.g. to debug) | `aws secretsmanager get-secret-value --secret-id grocery-dev/app --query SecretString --output text` |

## 11. Destroy everything

When you are done, delete everything this configuration created:

```powershell
cd deployment/aws/terraform
terraform plan -destroy -out tfplan   # shows what will be deleted
terraform apply tfplan                # deletes it (15-30 minutes)
```

(`terraform destroy` does the same in one command, asking "yes" first.)

With the dev settings everything goes, including the images (`ecr_force_delete = true`), the secrets
(`secret_recovery_window_days = 0`) and the database without a final snapshot. Two things outlive it on
purpose; check them in the console afterwards:

- **AWS Backup** keeps the EFS backups (AWS Backup > Backup vaults > `aws/efs/automatic-backup-vault`): delete the
  recovery points if you do not need them.
- In `staging` and `prod` RDS keeps a **final snapshot** (`grocery-<env>-mysql-final`; RDS > Snapshots).

If `destroy` stops with an error, run it again (some AWS deletions take a while to be visible to the next one);
if `deletion_protection = true`, set it to `false` and apply first. Finally, check **Billing > Bills** the next
day: the costs should stop.

## The MySQL database (Amazon RDS)

The application's data lives in **one Amazon RDS for MySQL 8.4 server** (`rds.tf`, built by the reusable module
[modules/rds-mysql](terraform/modules/rds-mysql/README.md)). Every service has its own database on it (`auth_db`,
`order_db` ...) and its own user that can only use that database, the same split as on a laptop.

| What | How it is set up | Setting |
|---|---|---|
| Access | Private subnets, no public address; only the ECS tasks' security group may connect (3306); TLS required for every connection | |
| Size | `db.t4g.medium` (2 vCPU, 4 GiB): fine for dev and a small shop | `rds_instance_class` |
| Disk | gp3, 20 GiB, grows by itself up to 100 GiB, encrypted | `rds_allocated_storage`, `rds_max_allocated_storage`, `rds_kms_key_arn` |
| High availability | Off in dev; on: a standby in another zone takes over in 1-2 minutes | `rds_multi_az` |
| Backups | Daily (00:30-01:30 India time), kept 7 days, restore to any second in that time | `rds_backup_retention_days` |
| Patches | Minor MySQL versions installed automatically, Monday 02:00-03:00 India time; never a major version by surprise | `rds_engine_version` |
| Admin password | Created, kept and rotated by RDS in Secrets Manager; nobody types or sees it | |
| Service passwords | Generated by Terraform (`grocery-dev/app` secret); `db-init` gives each user its password | |
| Debezium | Row-based full binary log, kept 24 hours, read by Kafka Connect over TLS | |
| Logs | Error log and slow query log (queries over 2 s) in CloudWatch Logs | `log_retention_days` |
| Monitoring | Enhanced Monitoring (every 60 s) and Performance Insights (which queries cost the most) | `rds_monitoring_interval` |
| Alarms | CPU > 80%, disk < 2 GiB, memory < 256 MiB, too many connections, by email | `alarm_email` |

### Open a MySQL prompt

The database cannot be reached from your computer (that is the point of a private database). `db-shell` starts a
short-lived container inside the VPC and connects you to it as the admin user:

```powershell
.\deployment\aws\scripts\db-shell.ps1      # needs the Session Manager plugin (link in "Everyday commands")
```

```sql
SHOW DATABASES;
USE order_db;
SHOW TABLES;
SELECT COUNT(*) FROM flyway_schema_history;   -- the migrations Flyway ran for this service
```

Type `exit` to leave; the container stops by itself. This is the **admin** user of the live database: read as much
as you like, change things only when you are sure (a wrong `DELETE` cannot be undone, only restored from a backup).

### Look at it in the AWS console

- **RDS > Databases > grocery-dev-mysql**: status, endpoint, Monitoring (CPU, connections, free space), Logs & events.
- **CloudWatch > Log groups > /aws/rds/instance/grocery-dev-mysql/slowquery**: the slow queries.
- **RDS > Performance Insights** (or CloudWatch Database Insights): which queries load the database right now.
- `terraform output mysql`: endpoint, port, admin user, secret and log groups.

### Make it bigger

Change `rds_instance_class` (e.g. `db.t4g.large`, or `db.m7g.large` for steady load) in `terraform.tfvars`, then
plan and apply. The server restarts with the new size: **a few minutes of downtime** without Multi-AZ (dev applies
it at once; staging and prod in the next maintenance window). With `rds_multi_az = true` the switch takes about a
minute. More disk needs nothing: it grows by itself up to `rds_max_allocated_storage`.

### Restore a backup

- **To a point in time** (e.g. 10 minutes before a mistake): RDS > Databases > grocery-dev-mysql > Actions >
  "Restore to point in time". This creates a **new** database next to the old one; look at the data there, then
  copy back what you need with `db-shell` (or point the environment at it, below).
- **From a snapshot into a new environment**: RDS > Snapshots shows the daily backups (and the final snapshot of a
  deleted staging/prod database). Set `rds_snapshot_identifier = "<snapshot name>"` in a **new** environment's
  `terraform.tfvars` before its first apply: its database starts with that data. (On an existing database the
  setting is ignored; Terraform never replaces a database because of it.)

### Upgrade MySQL

Minor versions (8.4.x) come automatically. A major version (a future 9.x) is a project of its own, on purpose
not a one-line change: test the application against it on a laptop and in a staging copy first. Then it needs
`allow_major_version_upgrade` in modules/rds-mysql/main.tf, a wider check on `rds_engine_version`, and a new
parameter group family; RDS blue/green deployments can switch over with almost no downtime.

## HTTPS and your own domain

1. Request a certificate in **AWS Certificate Manager** (same region as the shop): ACM > Request > public
   certificate > your domain (e.g. `shop.example.com`) > DNS validation. Add the CNAME record it shows to your
   DNS; after a few minutes the status is "Issued".
2. In `terraform.tfvars`:
   ```hcl
   certificate_arn = "arn:aws:acm:ap-south-1:123456789012:certificate/..."
   domain_name     = "shop.example.com"
   ```
3. Plan and apply. The load balancer now serves HTTPS on 443 and redirects HTTP to it; the services get
   `https://shop.example.com` as their public address (links in emails, photo URLs, the secure login cookie).
4. Point your domain at the load balancer: a CNAME record `shop.example.com` -> `terraform output -raw
   load_balancer_dns_name` (in Route 53: an "Alias" A record).

## Emails with Amazon SES

The platform sends emails (order updates, password reset). Without SMTP settings they are skipped; the in-app
notifications still work. With Amazon SES:

1. SES > Verified identities: verify your sender address or domain. A new SES account is in the "sandbox": it
   only sends to verified addresses until you request production access.
2. SES > SMTP settings > Create SMTP credentials: note the SMTP user name and password.
3. In `terraform.tfvars`: `mail_host = "email-smtp.ap-south-1.amazonaws.com"`, `mail_from = "no-reply@yourdomain"`,
   `mail_username = "<SMTP user name>"`; the password as `$env:TF_VAR_mail_password = "..."`. Plan and apply.

## Remote state

Terraform remembers what it created in a **state** file, by default `terraform.tfstate` in the terraform folder.
It contains the generated passwords, so it must stay private (it is in `.gitignore`), and losing it means
Terraform no longer knows your resources. For anything you keep, or as soon as two people work on it, store it in S3:

1. Create an S3 bucket (once; versioning and default encryption on, public access blocked).
2. Uncomment the `backend "s3"` block in `versions.tf` and fill in the bucket.
3. `terraform init -migrate-state` copies your local state into the bucket.

## Troubleshooting

| What you see | Why, and what to do |
|---|---|
| `No valid credential sources found` / `ExpiredToken` | Your AWS credentials are not set or expired: step 2, then `aws sts get-caller-identity`. |
| `terraform apply` fails creating MSK: version not supported | Set `msk_kafka_version` to a version from `aws kafka list-kafka-versions` (step 4). |
| A service never becomes healthy; the ECS console shows `CannotPullContainerError` | Its image with tag `image_tag` is not in ECR: run push-images (step 6) for it. |
| `ResourceInitializationError: unable to pull secrets` | Usually: the task cannot reach Secrets Manager (NAT gateway missing?) or `terraform apply` did not finish. Re-run plan/apply and read its errors. |
| A Spring Boot service restarts again and again | Read its logs (`aws logs tail /ecs/grocery-dev/<service>`). "Access denied for user" means db-init has not run (step 7). |
| The shop shows "502 Bad Gateway" / "503" | The services are still starting (3-5 minutes) or one of them fails: see the two lines above. |
| The shop works but no products are listed | The connectors are not registered or not running: step 9, and the logs of `kafka-connect`. |
| A connector shows `FAILED` | Its `trace` in the status says why. Run kafka-connectors again after fixing; check that db-init ran (Debezium user). |
| db-init fails: "Connections using insecure transport are prohibited" | Something connected without TLS: every client must use TLS (`--ssl-mode=REQUIRED`, `sslMode=REQUIRED`); the database requires it. |
| A service logs "Too many connections" / the connections alarm fires | The services' pools together exceed what the instance allows: a larger `rds_instance_class`, or smaller pools (`DB_POOL_MAX_SIZE` in a service's `environment` in services.tf). |
| db-shell: "The Session Manager plugin is missing" / the agent does not start | Install the plugin and open a new terminal; `enable_execute_command` must be `true`. |
| The alarm emails never arrive | Confirm the "AWS Notification - Subscription Confirmation" email (check the spam folder). |
| Logged out after reloading the page | Expected over plain HTTP (secure cookie): set up [HTTPS](#https-and-your-own-domain). |
| push-images fails building `kafka-connect`: "can't connect to remote host" for github.com | Your Docker cannot download the Prometheus JMX agent from GitHub (a proxy or firewall). Fix Docker's network access, or build the image on another machine. The agent is not used on AWS, so an image built without that download also works. |
| `Error acquiring the state lock` | Someone else (or an interrupted run) holds the lock. Wait, or if you are sure nobody runs Terraform: `terraform force-unlock <id>`. |

## Going to production

The dev settings are made to be cheap and easy to delete. For a real shop:

**Settings in a `prod` copy of terraform.tfvars**: `environment = "prod"`, `certificate_arn` and `domain_name`
(HTTPS), `load_demo_data = false`, `deletion_protection = true`, the database as
`rds_instance_class = "db.m7g.large"`, `rds_multi_az = true`, `rds_backup_retention_days = 14` and
`alarm_email = "<your team's address>"`, `redis_node_count = 2`,
`single_nat_gateway = false`, `az_count = 3`, `msk_instance_type = "kafka.m7g.large"`, `ecr_force_delete = false`,
`secret_recovery_window_days = 30`, `expose_api_docs = false`, larger `service_overrides` and `log_retention_days`,
and the [S3 backend](#remote-state).

**Known gaps to close first** (they need changes in the application, not only here):

- **The first super admin.** Without the demo data there is no admin account, and the app has no way to create
  the first one. Add one (for example an auth-service start-up step that creates a super admin from a secret)
  before launching.
- **Kafka over TLS.** The services connect to Kafka without TLS inside the VPC (the brokers are reachable only from
  the tasks). For TLS, the dead-letter producers in `KafkaConsumerConfig.java` (11 services) must build on
  `KafkaProperties.buildProducerProperties()` instead of a fixed map; then set `SPRING_KAFKA_SECURITY_PROTOCOL=SSL`
  and use `bootstrap_brokers_tls`.
- **Elasticsearch.** A single node on Fargate is fine for testing; for production use Elastic Cloud (it runs on
  AWS too) and set `elasticsearch_url`, or Elasticsearch on EC2 with EBS.
- **Social login** is off (`SOCIAL_LOGIN_ENABLED=false`); turning it on needs the providers' credentials as
  secrets ([docs/social-login.md](../../docs/social-login.md)).

**Further hardening**: AWS WAF on the load balancer, CloudWatch alarms (service CPU and memory, 5xx responses,
RDS storage), one IAM role and security group per service (least privilege), VPC endpoints for ECR, Logs and
Secrets Manager (less NAT traffic), and a CI/CD pipeline (e.g. GitHub Actions with OIDC, no stored keys) that runs
`terraform test`, pushes the images and applies.
